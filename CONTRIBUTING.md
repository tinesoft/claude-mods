# Contributing

This repository is one Nx workspace and one plugin marketplace, `tinesoft-mods`. Each mod lives in `mods/<name>/` and is an Nx project.

## Set up

Requires Node 22 or later, pnpm, and the `claude` CLI on the PATH.

```sh
pnpm install
```

`pnpm install` also installs the Git hooks (Husky).

The repository includes a dev container (`.devcontainer/`) with Node, pnpm, the GitHub CLI and Claude Code installed. Open the folder in VS Code and choose **Reopen in Container**.

## Repository layout

| Path                              | What it holds                                                                    |
| --------------------------------- | -------------------------------------------------------------------------------- |
| `mods/<name>/`                    | One mod: `hooks/`, `src/`, `tests/`, `.claude-plugin/plugin.json` and its README |
| `.claude-plugin/marketplace.json` | The `tinesoft-mods` marketplace, which lists every mod                           |
| `tools/claude-code-types/`        | Snapshots of the types Claude Code generates, one folder per version             |
| `tools/sync-plugin-version.mjs`   | Copies each mod's `package.json` version into its `plugin.json`                  |
| `tools/release/`                  | Nx release hooks                                                                 |
| `docs/design/<mod>/`              | Design notes and artboards                                                       |

## Development

```sh
pnpm nx dev session-activity       # claude --plugin-dir mods/session-activity
pnpm check                         # nx affected -t lint typecheck validate test
pnpm format                        # prettier --write .
```

Targets per mod: `lint`, `typecheck`, `validate` (`claude plugin validate . --strict`), `test` (`claude plugin test`) and `dev`. Claude Code loads `.ts` directly, so there is no build step.

Use the target-first form, for example `pnpm nx test session-activity`.

## Writing mod code

- Hooks receive `($, e, next)`. Use exactly these names, and never alias `$`.
- Every hook calls `next(e)` and returns its result, unless it deliberately answers for itself.
- Helpers in `src/` take plain data, never `$`, so `claude plugin test` can test them without the engine.
- `h` and `Fragment` are globals for JSX. Do not import them.
- Types come from the virtual module `claude-code`. Use `import type` for them; ESLint enforces it.
- `.claude-plugin/types/` is generated by Claude Code. Do not commit it.

## Testing

Tests live in `mods/<name>/tests/` and run with `claude plugin test`, which supplies the `claude-code/testing` mocks.

Run tests on the Claude Code version CI pins (see `CLAUDE_CODE_VERSION` in `.github/workflows/ci.yml`). A locally installed `claude` auto-updates, and a newer version can pass or fail differently than CI:

```sh
npm install -g @anthropic-ai/claude-code@2.1.302
```

Nx caches `lint`, `typecheck`, `validate` and `test` per `claude --version`, so changing versions reruns them.

## Adding a mod

1. Create `mods/<name>/` with `package.json`, `project.json`, `tsconfig.json` and `.claude-plugin/plugin.json`. Copy the shape of `mods/session-activity`.
2. Give `package.json` and `plugin.json` the same `version`, or `pnpm sync:check` fails.
3. Add the mod to `plugins` in `.claude-plugin/marketplace.json`.
4. Add a row to the Mods table in `README.md`.

The new Nx project name becomes a valid commit scope, and `nx release` picks up the mod from `mods/*`. Neither needs any other configuration.

## Updating the pinned Claude Code version

`typecheck` reads `tools/claude-code-types/<version>/index.d.ts`, a snapshot of the types Claude Code generates in `.claude-plugin/types/`. When you move to a new Claude Code version:

1. Add the new snapshot to `tools/claude-code-types/<new-version>/index.d.ts`.
2. Update the version in `CLAUDE_CODE_VERSION` in `.github/workflows/ci.yml` and `.github/workflows/release.yml`, in each mod's `tsconfig.json` `include`, and in the "CI tests against" line in `README.md`.
3. Run `pnpm nx run-many -t lint typecheck validate test` on that version.

## Branches and commits

- Branch from `develop` as `feat/...`, `fix/...` or `chore/...`, and open a PR to `develop`. `main` is release-only.
- Commits follow Conventional Commits. The scope is a project name (`session-activity`) or one of `repo`, `ci`, `deps`, `release`. CI also checks the PR title against the same rules.
- Do not edit versions or `CHANGELOG.md` by hand. `nx release` owns them.
- Releases come from `main`. Fast-forward `main` to `develop` with `git push origin develop:main`, never a merge commit, so `main` keeps the same commits `nx release` reads.

The Git hooks run on every commit:

- `pre-commit` runs Prettier and `eslint --fix` on staged files, and `claude plugin validate --strict` on each touched mod when `claude` is on the PATH.
- `commit-msg` runs commitlint.

## Before you push

```sh
pnpm check
pnpm sync:check                    # plugin.json versions match package.json
```

CI runs the same, plus `claude plugin validate . --strict` at the repository root, on the pinned Claude Code version.

## Releases

Each mod versions independently and is tagged `<mod>@<version>`.

- Push to `main`: `release.yml` runs `nx release --skip-publish`, which bumps each mod with releasable commits, updates its changelog, syncs the version into `.claude-plugin/plugin.json` (`tools/sync-plugin-version.mjs`), commits, tags and creates a GitHub Release. It then back-merges `main` into `develop`.
- One mod by hand: run the `Release` workflow with `project` and an optional `specifier` (`patch`, `minor`, `major` or an exact version). The first release of the repository must be run this way with specifier `0.1.0`: until a release tag exists, the automatic run on `main` skips, because nx would tag it `0.1.1`.
- Preview locally: `pnpm nx release --projects=session-activity --dry-run`.
